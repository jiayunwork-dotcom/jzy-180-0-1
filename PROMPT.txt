来料检验这件事，我们质量部一直是查表加手算：一次抽样还凑合，二次抽样的接收概率和平均样本量基本算不清，正常、加严、放宽之间什么时候该转，全靠检验员在台账上数格子，数错了也没人发现。客户的供应商质量工程师这次把话挑明了，要看到 OC 曲线、风险数据和转移记录。我打算做一个后端服务，把这几块都收进来。

先是方案档。档有名字，存进数据库，可以新建、修改、删除、按名查询。一次抽样由样本量 n、接收数 c 定义；二次抽样则是首轮样本 n1 配接收数 c1 与拒收数 r1，再加二轮样本 n2 及两轮合计的接收数 c2，要求 c1<r1≤c2+1。档可带批量 N：带了就用超几何分布，没带用二项分布，也可显式要泊松近似，此时响应要标明是近似，n·p 超过 5 时给警告。组合数与概率一律在对数域算，n 到几千也不许溢出或悄悄变成 0。

针对一个档能算：一组不合格率 p 下的接收概率 Pa；二次抽样另给平均样本量 ASN；带 N 且拒收批全检时的平均出厂质量 AOQ、其最大值 AOQL 与对应 p、平均检验总数 ATI；给定 AQL 与 LTPD 时，还要报出 α=1−Pa(AQL)（生产方风险）与 β=Pa(LTPD)（使用方风险）。画曲线时 p 的范围和点数可以指定，点数不超过 500。反向设计也要：给 AQL、α、LTPD、β，找满足两个风险约束且 n 最小的一次方案，n 相同取 c 小的；二次方案限定 n2=n1 或 n2=2·n1，在可行方案中取 p=AQL 处 ASN 最小者；搜索有上限，找不到就明说无可行方案。

新增的重点是检验流。一条检验流绑定正常、加严、放宽三个方案档，逐批录入检验结果（批号、检验时间、样本中的不合格数，二次抽样还有第二样本的不合格数），服务按当前所处的严格度判定接收与否，并按 GB/T 2828.1 的转移规则推进状态：正常下连续不超过 5 批里有 2 批不接收转加严；加严下连续 5 批接收回正常；正常下转移得分达到 30 且流上标记了生产稳定、主管同意时转放宽，转移得分按标准的加分与清零规则累计；放宽下出现一批不接收或生产稳定标记被撤销即回正常；加严下累计不接收达到 5 批则暂停检验，要人工恢复后以加严重新开始。每一批的记录里要能看到当时的严格度、所用方案、判定结果和转移得分。

麻烦在于历史会被改。补录一批更早时间的结果、删掉一批、或修正某批的不合格数，之后的状态都可能跟着变。不管怎么改，检验流的当前状态以及每一批当时的严格度、判定和得分，都必须与按时间顺序从头重放全部批次得到的结果逐字段相同。是每次改动都整条重放，还是从被改的那一批起增量重算、再配合检查点，这由你权衡：流很长时整条重放贵，增量又容易在得分清零、暂停这些边界上算漏。选定后在交付说明里写清楚理由和代价。多个客户端同时往同一条检验流录入或补录，不允许出现丢批、重复计分或状态交错；不同检验流之间互不阻塞。

测试要证明：不合格率为 0 时 Pa 恰为 1；不合格率为 1 且 c<n 时 Pa 恰为 0；样本量不变而 c 增大，Pa 曲线整条不下降；c 固定 n 增大，0<p<1 处 Pa 下降；N 很大时超几何逼近二项；把二次方案退化成 n2=0、c1=c2、r1=c1+1 后，算出来要和对应的一次方案分毫不差；ASN 在 n1 与 n1+n2 之间；ATI 在 n 与 N 之间；AOQL 不小于曲线上任一点的 AOQ；设计出的一次方案满足约束，样本量减一后任何 c 都不再满足。转移方面，要有构造好的批次序列分别触发每一种转移与暂停，并用随机打乱的补录、删改序列去比对增量结果和从头重放；并发录入要有压测式用例。另附 n=80、c=2 的一次方案作可以手算核对的例子。n<1、c<0、c≥n、p 不在 [0,1]、批量 N 比样本量还小、AQL≥LTPD、α 或 β 落在 (0,1) 之外，以及不合格数超过样本量，都拒绝并指出字段。

用 Go 1.23 + Echo，档、检验流与批次存 PostgreSQL 16。分布与对数域组合数、OC/ASN、AOQ 与 ATI、风险与方案搜索、转移状态机、历史重算、存储、HTTP 层各自成包，代码按这些职责拆成多个模块和文件，状态机与重算逻辑别挤进同一个大文件。服务镜像基于 golang:1.23-alpine 构建，数据库容器用 postgres:16-alpine 的镜像，两者写进同一份 Compose 编排；只提供 HTTP 接口，不做前端。
